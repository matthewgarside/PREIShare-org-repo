# Embeddings learner notes (PREIshare)

## Plain-language definition
An embedding turns text into a list of numbers so a computer can compare meanings.
For PREIShare, the text could be a property description or an investor’s search
phrase. Similar property descriptions should have number lists that are close
together, even if they use different words.

## Tiny intuition (not real model output)
These made-up numbers are just for learning. They are not actual embeddings
generated by a model. Imagine a toy 3-number embedding to picture “near” vs.
“far”:

- "quiet cabin near water" → [0.9, 0.8, 0.1]
- "peaceful wooden vacation home overlooking a lake" → [0.88, 0.82, 0.12] (nearby)
- "modern downtown loft near shopping and restaurants" → [0.1, 0.2, 0.95] (far from the cabin)

Real embeddings are much longer lists. The idea is the same: text with similar
meaning gets number lists that are close when compared.

## PREIshare examples from our requirements
- An investor searches for “quiet cabin near water.”
- One listing describes a “peaceful wooden vacation home overlooking a lake.”
  That should be a better match because it describes a quiet home beside water,
  even though it does not use the exact words “cabin near water.”
- Another listing describes a “modern downtown loft near shopping and
  restaurants.” It may be a good listing for a different search, but it does
  not sound like a quiet lakeside cabin.
- An investor could also search for “rental upside.” A listing that says a
  property has the potential to earn more rental income could be relevant,
  even if it does not use the phrase “rental upside.” This is a possible match,
  not a promise that the property will earn more.

## Generation vs storage (do not mix these up)
| Stage | What happens | Where |
| --- | --- | --- |
| Generation | Text goes into an embedding model/API; a number-list comes back | App/code side (later: TypeScript module) |
| Storage | That number-list is saved with the property row so it can be searched later | Database (planned: Supabase PostgreSQL + pgvector) |

When a property is added or updated, its text can be sent to an embedding model
to generate its number list. PostgreSQL with pgvector can save that list with
the property so search can use it later. Saving it means we do not need to
generate a new embedding for every property every time someone searches.

For a search, the investor’s query can be turned into an embedding, then
compared with the property embeddings that were already saved. How to compare
and order the results is for a later lesson.

## Misconceptions to watch for when reviewing agent code later
- Embeddings are not just regular strings or a list of keywords. They are
  numbers that represent text in a way a computer can compare.
- Semantic search compares meaning, not just exact matching words. A search
  for “cabin near water” could match a listing that says “lakeside vacation
  home.”
- Generating an embedding and storing it are different steps: a model makes
  the number list, and a database saves it.
- PostgreSQL does not automatically make embeddings just because property
  information is saved. The application still needs to send text to an
  embedding model and save the result.
- Similar embeddings are close numerically according to a comparison, not
  simply next to each other in a list of properties. Their place in a list
  does not tell us how similar they are.

## What I can explain to a teammate in 60 seconds
An embedding is a list of numbers made from text that helps a computer compare
meaning. If someone searches for a quiet cabin near water, a peaceful home by a
lake could match even if the listing uses different words. The model generates
the numbers, and PostgreSQL with pgvector can store them so they are ready for
later searches. The database does not make those numbers by itself. We still
need to decide how to compare results and check that the matches make sense.
